# 开发流程与阶段门

## 1. 流程

本项目采用轻量迭代流程，但保留完整可追踪产物。

| 阶段 | 主要活动 | 必备输出 | 退出条件 |
|---|---|---|---|
| 1. 需求分析 | 场景澄清、竞品调研、范围划分、验收定义 | 调研、PRD、用户故事、数据/非功能需求、追踪矩阵 | 用户确认需求基线 |
| 2. 产品与 UX 设计 | 页面结构、流程、线框图、交互状态 | 信息架构、流程图、可点击或静态原型、设计评审记录 | 核心流程无阻塞，状态齐全 |
| 3. 技术设计 | 架构、数据库、备份格式、安全与测试策略 | 架构文档、ER 图、API/模块契约、ADR、测试计划 | 关键风险有方案且可验证 |
| 4. 迭代实现 | 按垂直切片开发、代码审查、单元测试 | 源码、构建脚本、迭代记录、变更日志 | 每个故事满足完成定义 |
| 5. 系统测试 | 功能、数据一致性、恢复、性能、兼容性测试 | 用例、自动化结果、缺陷清单、测试报告 | P0/P1 缺陷清零，发布标准通过 |
| 6. 发布交付 | 签名构建、安装验证、文档归档 | APK、校验值、发布说明、用户手册、已知问题 | 目标设备安装与数据流程验证通过 |
| 7. 维护迭代 | 反馈、备份兼容、缺陷修复、需求变更 | 问题记录、迁移方案、版本路线图 | 持续进行 |

## 2. 版本与变更规则

- 需求标识使用 `FR-*`（功能）、`DR-*`（数据）、`NFR-*`（非功能）。
- 用户故事使用 `US-*`；测试用例后续使用 `TC-*`。
- 已确认的需求形成基线。新增或修改需求必须记录原因、影响和决策日期。
- 数据库与备份格式均须带版本；任何破坏兼容性的变更必须提供迁移验证。
- 每次可安装交付保存版本号、构建时间、Git 提交、SHA-256 和测试结论。

## 3. 完成定义（Definition of Done）

一个用户故事只有同时满足以下条件才算完成：

1. 验收标准全部通过；异常、空状态和边界条件已处理。
2. 核心逻辑有自动化测试，关键页面通过人工验证。
3. 无新增高危安全/隐私问题，无未经说明的权限。
4. 相关文档、需求追踪和变更日志已更新。
5. Debug 与 Release 构建均成功，目标设备可安装运行。
